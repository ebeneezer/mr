# MRMAC Reference Manual Contract

## Scope

Applies to the standalone MRMAC reference source:

- `documentation/manuals/mr-macro-reference.tex`

It governs later additions, corrections and layout work in that manual. It does
not govern the user manual or a future technical manual.

## Authority

The manual documents implemented MRMAC semantics.

- `mrmac/mrmac.c` is the canonical grammar and compiler source.
- `mrmac/MRVM.cpp` and the relevant MRMAC architecture contracts define
  executable intrinsic and procedure semantics.
- The original ME Macro Language Reference Guide is a historical structural and
  compatibility source. It is not authority for MRMAC behavior.
- Unimplemented, obsolete or incompatible MEMAC behavior must never be
  documented as available in MRMAC.

The manual source and its prose are English. MRMAC identifiers, syntax and
examples remain exact English source language.

The reference is the only MRMAC manual supplied with a normal package
download. It is self-contained and starts from a reader with no prior MRMAC,
MEMAC or editor-macro knowledge. Historical PDFs are neither a prerequisite
nor an implicit source of omitted explanations.

## Document Structure

The original reference guide is a guide, not a mandatory chapter sequence. The
manual must use these parts in this order:

1. Language Fundamentals
2. Editor Automation
3. Interaction and UI
4. Runtime and Integration
5. Debugging

Language fundamentals group macro structure, comments, labels, declarations,
types, constants, expressions, control flow and macro composition.

Editor automation groups text, cursor, tab, indentation and block operations.
Interaction and UI groups typed UI procedures, dialogs, modeless MMP controls
and macro invocation through keymaps.

Runtime and integration groups macro catalog operations, files, windows,
external commands, globals, settings-adjacent procedures and execution
sessions.

The historical Word Processing and DOS Shell chapters are not recreated. Their
unimplemented commands are mentioned only as compatibility footnotes at the
nearest relevant MRMAC operation.

The historical runtime-error and compiler-error tables are replaced by these
two chapters:

- `Debugging MRMAC Macros`
- `Inspecting State and Diagnosing Failures`

They document the implemented source-level debugger: starting a debug session,
breakpoints, continue/pause/stop, stepping, source location, variables,
watches, expression evaluation and diagnostic output. They must not invent a
stable numeric error-code taxonomy.

The manual ends with current MRMAC examples, compatibility notes and the
generated command index.

## MRMAC Extension Marking

Every MRMAC extension relative to MEMAC must be marked in the outer margin by
a vertical change bar. The LaTeX source uses the `changebar` package and wraps
the complete extension-specific explanatory block in `changebar` markup.

The bar is a semantic marker, not decoration. An extension includes a new type,
collection operation, intrinsic, procedure, runtime concept, debugger feature,
typed UI primitive, modeless MMP primitive or altered documented behavior.
The marker must remain when a later edit changes local prose or pagination.

## MEMAC Compatibility Notes

For a comparable MEMAC command that MRMAC does not implement, add a concise
footnote at the relevant MRMAC discussion. The footnote names the historical
command and states that it is not available; it must not speculate about an
emulation or silently substitute a different operation.

Do not create empty historical chapters merely to collect unavailable commands.
Compatibility notes explain local migration decisions; they are not a second
language reference.

## Generated Navigation

The table of contents is generated by LaTeX. Every documented MRMAC keyword,
intrinsic and procedure must receive an alphabetical index entry with its page
reference. The command index is generated with `makeindex` and printed in the
manual.

New documented commands require all of the following in the same change:

- a syntax and semantic description,
- an extension marker when applicable,
- a compatibility footnote when a comparable MEMAC command is unavailable,
- an index entry.

Each subject chapter begins with a short, zero-knowledge introduction and a
local primitive map. The map lists every primitive explained by that chapter,
states its role and purpose, and gives a generated hyperlink and page reference
to its detailed entry. The detailed entries follow in that same chapter in a
useful learning and lookup order. A reader must not need to search a detached
catalogue for the first complete explanation of a primitive.

The local maps, the table of contents and the alphabetical command index are
complementary navigation mechanisms. None replaces the others.

## Primitive Reference Entries

The command catalogue is a reference, not a grouped name inventory. Every
implemented MRMAC keyword, intrinsic, procedure, built-in constant and
built-in variable normally has its own entry at the nearest subject chapter.
Each entry has a stable local navigation target and contains, in this order:

1. the canonical source signature,
2. a positional parameter description, including the result value where the
   primitive is an intrinsic,
3. an executable semantic description, and
4. one complete example macro using that primitive.

A homogeneous family of symbolic constants may use one combined entry when all
of its member names retain individual local map rows, navigation targets and
index entries. The combined entry must list every name and value in a
`verbatim` environment and provide one representative complete example macro.
This exception is limited to a true semantic family, such as the fixed colour
palette; it must not combine unrelated constants for layout convenience.

The compiler signature tables are authoritative for argument count and type.
The VM implementation is authoritative for parameter meaning and observable
effect. A catalogue entry may refer to common coordinate, colour or callback
conventions, but it must still name every parameter in its signature.

Every fragment of MRMAC source, including a signature, declaration, expression
or complete macro, is typeset in a LaTeX `verbatim` environment. The manual
does not use an inline-code font as a substitute for a source fragment.

## Examples And Accuracy

Examples must compile against the current canonical compiler where practical.
They must use current MRMAC forms and must not preserve MEMAC syntax solely for
historical appearance.

The reference describes only behavior present in the checked source tree.
Planned UI primitives, debugger capabilities and runtime features belong in
planning documents, not in the reference manual.

## Required Documentation Checks

Before handoff of a manual change, run the LaTeX sequence:

```sh
pdflatex -interaction=nonstopmode mr-macro-reference.tex
makeindex mr-macro-reference
pdflatex -interaction=nonstopmode mr-macro-reference.tex
pdflatex -interaction=nonstopmode mr-macro-reference.tex
```

Visually inspect the resulting PDF for page format, table of contents, command
index, change bars, footnotes, code listings and overfull text. Apply the root
build rule before handoff as well.
