\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}

This is neither a class catalogue nor retrospective self-congratulation. It
explains why \mr{} is built differently from a conventional terminal editor in
several important respects, which experiments were abandoned, and which limits
remain despite the successes. Its sources are the repository, architecture
contracts, planning documents, Kanban entries, and version history. Where
those sources do not support a claim, this manual does not make it.

The MRMAC Reference Manual documents the language and its primitives. This
book tells a different story: how document handling, runtime, UI, and user
customisation became one system whose parts do not quietly take ownership of
one another.

\mainmatter
\part{Why \mr{} exists}

\chapter{Not another editor}

\mr{} began with the intention of carrying the character of Multi-Edit
forward, not as a nostalgic surface but as a way of working. An editor should
be immediate, keyboard-capable, and at home in a terminal. At the same time,
it should not treat large files, many windows, build output, and automation as
foreign bodies.

This heritage produced several non-negotiable goals: speed, a practically
unbounded workspace, reliable editing operations, extensibility and
customisation by the user, and responsiveness under load. The close
relationship between \mrmac{} and the compiled application is therefore not
an item at the end of a plugin list. It is part of the product's definition.
Decoupling matters just as much: a document may be edited while derived work
is being produced, but a background result must not write itself into a screen
that has moved on in the meantime.

The guiding principle is consequently not \emph{as many features as possible},
but \emph{as much productive power as possible without sacrificing control}.
Each chapter asks a concrete question: which technical problem threatened that
goal, what idea shaped the solution, and where did \mr{} deliberately reject a
seemingly convenient alternative?

\chapter{Standing on the shoulders of others}

\mr{} does not attempt to carve every wheel from scratch. Its distinctive
character comes precisely from the boundary between inherited foundations and
its own semantics.

The working model comes from Multi-Edit and the MEMAC tradition: windows,
blocks, macros, and personal interaction should be ordinary parts of editing
rather than exceptional add-ons. \mrmac{} preserves that lineage, while being
its own compiled, in-memory runtime.

Magiblot's TVision provides the terminal-native object world. TVision owns
focus, Z order, event routing, view lifetime, dialogs, and drawing dispatch.
\mr{} extends that world through its intended mechanisms instead of placing a
second screen model or event loop beside it. The dependency is maintained as
an upstream subtree with a small patch queue. This is a deliberate
relationship: upstream remains identifiable and local changes remain
reviewable.

The frequently proposed alternative is not really TVision \emph{or}
\texttt{ncursesw}. \mr{} links against \texttt{ncursesw}; it is part of the
terminal platform beneath TVision. The actual choice was TVision rather than
building a window, focus, dialog, and drawing system directly on bare curses.
For an editor with virtual desktops and a long Multi-Edit UI tradition, that
was a useful trade: less invented infrastructure, more energy for documents
and runtime behaviour.

PCRE2 supplies Perl-compatible regular-expression semantics for search and
multi-file work. POSIX supplies, among other things, \texttt{mmap}, processes,
and pipes. Pango and Cairo support PDF export. These components are not hidden
MR subsystems. Each solves a clearly bounded problem; responsibility for
placing its results in the editor model remains with \mr{}.

\part{The document as workspace}

\chapter{A gigabyte file in five milliseconds}
\label{ch:large-files}

The striking number needs to be told accurately. The \texttt{enwik9} file
used in the repository contains exactly 1,000,000,000 bytes and 13,147,025
lines. On the measured development machine, \mr{} makes this document
available as an editable document in about five milliseconds.

That does not mean that a gigabyte is copied from storage and fully analysed
in five milliseconds. The number is the measured \emph{mapped load} time.
\mr{} opens a regular file as a private, read-only memory mapping and builds
its logical document state on top of that mapping. The operating system brings
pages in on demand; the editor does not first copy the original into a mutable
string.

A Piece Table sits above the mapping. The original remains the source of
pieces, new input goes into the add buffer, and the logical order is expressed
as references to those sources. An edit therefore does not move a gigabyte of
text. It changes piece boundaries and adds new data to the add buffer. This
model serves more than load time: it makes editing, snapshots, undo boundaries,
and later derived work variations of the same data economy.

Figure~\ref{fig:piece-table-snapshot-boundary} on
page~\pageref{fig:piece-table-snapshot-boundary} makes the ownership boundary
explicit. A background task receives a versioned read snapshot, never the
mutable live object. It may return a derived result or a staged edit, but it
cannot adopt that work itself.

The line index then warms independently from interaction. Until an exact total
is available, the editor uses a bounded estimate and local cursor-relative
navigation. The enwik9 milestone was therefore not satisfied by a fast
``opened'' message. It required immediate restore and drawing, responsive
scrolling and large jumps, and eventual exact metrics without a hidden
UI-thread full scan.

\section{Finite packets instead of deferred serial work}

The general task envelope, one-shot worker model, and adoption path are
described in Chapter~\ref{ch:coprocessor-derived-work}. For large documents,
the relevant domain fact is that line index, display width, syntax, folding,
and minimap are separate pipelines. Their finite packets carry a concrete
execution owner and a versioned \texttt{ReadSnapshot}; their domain ledgers,
ordering rules, and retained results are deliberately different. Focus loss
is not a pause signal.

Line-index packets are arithmetic byte windows of eight MiB. The UI does not
search for line boundaries before submission. A document-bound ledger records
the contiguous prefix confirmed from BOF, out-of-order packet results, and
active reservations. Planning covers gaps only, so a cursor jump may start new
BOF- and EOF-directed work without duplicating an older packet. Sparse line
checkpoints are retained every 4,096 line breaks; the exact total becomes
authoritative only when the confirmed prefix reaches EOF. Goto-line and cold
large-file drawing consult confirmed checkpoints or wait for ledger progress;
they no longer count linearly from BOF on the UI thread.

Display-width work begins only after that exact line index exists. A generation
splits the indexed lines into at most one packet per allowed core. Each worker
addresses its first line once and then advances linearly with
\texttt{nextLine}; it does not repeat \texttt{lineStartByIndex} for every
line. The result is one maximum terminal-cell width per packet, not a cache of
all line widths. Syntax, folding, minimap, indentation, and rendering consume
the common line-addressing basis, not the display-width result.

Syntax and folding have a stricter adoption rule because their state moves
forward through the document. Text acquisition may run in parallel, but a
packet becomes visible only from a confirmed \texttt{stateIn}. A speculative
packet whose entry state differs is discarded and only that finite packet is
recomputed from the confirmed predecessor. Syntax publishes sparse state
checkpoints and only the token runs required for the viewport and prefetch
range. Folding similarly publishes a checkpoint containing its structural
stack and bounded language look-back. Neither pipeline invents a closing state
at a packet boundary.

The minimap likewise uses finite text and overlay projection packets. Its
editor-local windowing, reuse, and rendering rules belong to
Chapter~\ref{ch:minimap}; here it matters that the minimap consumes the common
line-addressing basis without becoming another line or syntax index.

projections at one viewport position together with their task telemetry. The

\section{Moving windows, checkpoints, and ledgers}
\label{sec:warmed-range-ledger}

Figure~\ref{fig:deferred-scan-windows} on
page~\pageref{fig:deferred-scan-windows} shows the common shape without
erasing the domain differences. A viewport demand creates a generation and
reserves only uncovered packet spans. Finite workers may complete out of order
and may remain useful after a cursor jump. The ledger first accepts matching
results; the domain then advances its confirmed frontier or visible window as
its ordering rule allows.

For syntax, BOF direction means context acquisition before the viewport, never
backward lexical evaluation. A confirmed line state may serve directly as the
next anchor; otherwise sparse checkpoints lead back towards BOF. Packet count
is additionally limited by a minimum useful grain of sixteen lines. For
folding, fixed 65,536-line acquisitions populate a document-wide canonical
context chain. Structural validation advances in checkpoint order, while the
visible segment projection remains immutable and searchable by segment
boundaries. Cursor movement within the same document version does not rebuild
that canonical chain.

For the minimap the ordering constraint is weaker. Its acquisition window is
directionally biased and covers at least four times the allowed-core count in
visible minimap windows. At most one packet per allowed core is materialised,
and the ledger retains a bounded number of complete windows. Small movement
inside the warmed region therefore creates no new worker wave. An edit,
language change, geometry change, or incompatible document version invalidates
only the state whose key includes that dimension.

\section{Line-break scan primitives}

Line navigation, line numbering, packet acquisition, and Piece Table scans
require the same three operations: locate the next line break, locate the
previous line break, and count line breaks in a byte range. These operations
are implemented in the line-index core. On x86 builds with SSE2, the core loads
sixteen bytes at a time, compares them with carriage return and line feed, and
converts the resulting bit masks into positions and counts. A scalar
implementation is the fallback for platforms without the vector path.

The scanner carries CRLF state across vector blocks and handles the scalar
tail, preserving the same line model at vector and chunk boundaries. The
counting primitive operates on direct mapped text and on individual Piece Table
chunks; the direct path also uses vector search in both directions. Packet
boundaries preserve CRLF semantics, and a sequential line range is addressed
once before advancing locally. All derived pipelines therefore consume one
line model rather than maintaining feature-specific text indexes.

\chapter{Derived work must not stop the editor}
\label{ch:coprocessor-derived-work}

The coprocessor is a lifecycle and delivery boundary, not a fixed worker pool
and not a general executor from which a worker may call back into the
application. Four finite-work lanes classify I/O, compute, minimap, and macro
work for telemetry and dispatch. Registered external sources use a separate
lifetime-bound route. Neither mechanism serializes independent owners.
Figure~\ref{fig:coprocessor-lanes} on
page~\pageref{fig:coprocessor-lanes} shows the complete path from a domain
packet to an adopted result.

\section{Task envelope and scheduling boundary}

\texttt{submit} and \texttt{submitPacket} construct a \texttt{TaskInfo} with a
unique task identifier, lane and task kind, execution-owner kind and owner-local
identifier, document identity and base version, cancellation state, and---for
packet work---generation, direction and half-open span. Document-derived
submitters capture the coherent read snapshot or immutable input on which the
task operates. The document/version pair is an adoption ticket, not permission
for the worker to inspect a live view.

The old one-shot coalescing API was removed because every invocation created a
new execution state and therefore had no shared queue in which to find an older
key. Coalescing now belongs to the owning domain: a pane may retain one active
task and one newest requested successor, while a ledger may reserve already
covered spans. This keeps scheduler mechanics separate from semantic
equivalence.

Every ordinary finite submission creates its own \texttt{std::thread}. The
worker receives the next monotone \texttt{workerOrdinal}; its assigned core is
computed once as

\begin{center}
\texttt{allowedCoreIds[workerOrdinal \% allowedCoreIds.size()]}
\end{center}

and remains stable for that worker's lifetime. The number of workers is not
capped by the number of cores. More workers continue around the same modulo
sequence, so independent work does not become a lane-wide queue merely because
all cores already have an assignment.

\section{Lanes classify work; owners define independence}

Exactly four ordinary lanes appear in the coprocessor snapshot and Performance
Panel: \texttt{Io}, \texttt{Compute}, \texttt{MiniMap}, and \texttt{Macro}.
Four is not a CPU topology, a concurrency limit, or a priority ladder. The
number follows from four observably different finite-work contracts. Collapsing
them would hide why work exists and which result path must validate it; adding
a lane for every feature would merely duplicate task kind and owner identity.

\paragraph{I/O.}
The \texttt{Io} lane classifies finite command, Git, process, and similar
operating-system work whose dominant uncertainty is external latency. Its
normal result describes command completion, output, or failure rather than a
document-derived projection. The classification keeps such latency and error
behaviour visible without granting a finite command the lifetime semantics of
a registered stream.

\paragraph{Compute.}
The \texttt{Compute} lane carries deterministic derived work over immutable
input: line-index and display-width packets, syntax and folding, Bento
diagnostics and outlines, HexBento projections, and File Compare stages. These
results are normally accepted against document identity, version, generation,
span, pane role, or another domain checkpoint. Bento is therefore a task kind
and pane owner on \texttt{Compute}, not a fifth lane.

\paragraph{MiniMap.}
The \texttt{MiniMap} lane identifies per-editor text-density and overlay
projection packets. They are computational, but their demand is driven by
viewport movement, geometry, visible row windows, and rapidly changing overlay
state. Keeping this class separate makes minimap churn, coverage, and adoption
visible independently of canonical line, syntax, and fold preparation. It does
not give the minimap a privileged worker or a private result mailbox.

\paragraph{Macro.}
The \texttt{Macro} lane identifies finite \texttt{MacroJob} executions. Their
owner is an Execution Session, and their results differ from document
projections by carrying macro log, session, or staged-effect state. VM
profiling and session routing are described in
Chapters~\ref{ch:mrmac-vm} and~\ref{ch:execution-sessions}. A paused macro
holds its VM/session state but no lane worker.

The distinction is thus semantic and operational. The lane name gives
telemetry and dispatch the first workload category; \texttt{TaskKind}
identifies the concrete operation; execution-owner kind and owner-local ID name
whose work it is; document/version and generation fields decide whether a
result may still be used. No one of those axes can replace the other three.
None of the four lane names denotes a shared single-worker FIFO.

An editor window, Bento pane, Execution Session, external source, or channel is
an execution owner. Several packets may belong to one owner, and the same
document may be viewed through several independent owners. Result routing uses
the exact owner and task identity; two windows over the same document cannot
clear or adopt one another's work.

The deliberate exception is a technically blocking source whose lifetime
consists of \texttt{poll()}, \texttt{read()}, process wait, or an equivalent
external wait. The implementation tags this route as \texttt{Lane::Extern},
but does not include it among the four finite lane snapshots. Registered
sources have their own source snapshot and lifetime because they are not
one-shot work. A registered file, journal, device, network, or pipe source may
keep one exclusive worker until EOF, close, cancellation, error, or process
termination. It never carries another owner's work. Journal cancellation
closes the local read side, terminates and reaps the process group with bounded
escalation, and publishes the exact viewer target before the worker is joined.

An MRMAC Execution Session is not such a source merely because it is
asynchronous. A finite VM computation is a \texttt{MacroJob}; a session paused
for UI adoption holds logical execution state but no blocked worker. If that
session owns a real external process or terminal source, source and session
lifetimes remain separate.

\section{Worker completion and the result mailbox}

The one-shot worker publishes creation, assignment, queue, running, and
result-ready transitions, performs its finite task outside scheduler locks,
and appends the immutable result to the mutex-protected central FIFO.
Exceptions become failed results; cancellation remains cooperative and is
checked at bounded points. No lane has a private path to the screen.

\texttt{pump(maxResults)} drains at most the requested count---eight by
default---whereas \texttt{pumpFor} stops after the supplied time budget once a
result has been handled. Both invoke the installed result handler on the UI
thread. The central \texttt{handleCoprocessorResult} performs payload dispatch;
it does not replace the owning domain's validation.

Dispatch locates the exact task-owning editor, pane, session, source, or
channel. The domain checks owner, task, generation, document and version, plus
its own geometry, language, checkpoint, or conflict conditions. A stateful
pipeline may first mark a result \texttt{accepted} in its ledger and later
\texttt{adopted} into the visible model. A mismatch produces
\texttt{discarded}; it is never rebased implicitly.

\section{Cancellation and observability}

\texttt{cancelTask} sets the shared cancellation state; a worker is not killed
at an arbitrary instruction. Worker lifetime uses explicit \texttt{std::thread},
a directly visible atomic stop state, \texttt{condition\_variable}, and join.
Retirement joins only workers already marked finished, so normal UI pumping
does not wait for running work. Synchronous join remains the unavoidable
shutdown lifetime barrier.

The performance snapshot separates identities from measurements. It reports
the execution owner, task, \texttt{workerOrdinal}, OS thread identifier and
assigned core as distinct fields. Its bounded lifecycle ring records
\texttt{created}, \texttt{assigned}, \texttt{queued}, \texttt{running},
\texttt{result-ready}, \texttt{accepted}, \texttt{adopted},
\texttt{discarded}, \texttt{stopping}, and \texttt{finished}. Queue, run,
accept, adopt and total durations, packet generation, direction and span are
observability outputs only; they never become semantic inputs to a projection.

\section{Geometry and the sampling window}

The effective edit settings select \texttt{OFF}, \texttt{LEADING}, or
\texttt{TRAILING}, a total minimap width from 2 through 20 cells, and a
single-cell viewport-marker glyph. \texttt{TextViewportGeometry} reserves the
body, marker, and optional separator columns. The body receives all but one
cell of the configured width; the marker occupies the independent
\texttt{infoX} column. The normal and File Compare palettes provide separate
colours without changing the generated patterns.

The editor projection request contains body geometry, visible text-row count,
viewport width, top line, exact or estimated total line count, document
identity and version, and a read snapshot. It is scheduled from semantic and
viewport changes, not created by \texttt{draw()}. Braille mode is used only
when TVision reports the full Braille glyph as one terminal cell. Otherwise
the renderer falls back to one block cell per sample.

\texttt{samplingWindowFor} assigns four source-line samples to every minimap
row in Braille mode and one in fallback mode. For $R$ minimap rows, its capacity
is therefore $4R$ or $R$ lines. A document no larger than that capacity uses
the interval $[0,totalLines)$. A larger document uses a capacity-sized window
centred on \texttt{topLine}, clamped first at BOF and then at EOF. The minimap
therefore describes the cursor-near region at useful resolution rather than
compressing an arbitrarily large document into the same fixed row count.

The projection key contains document identity and version, row and body
dimensions, viewport width, renderer mode, and the exact sampling interval.
The warm-window ledger retains at most
\(\max(4,2\cdot\textit{allowedCoreCount})\) complete, compatible windows. A
new directional acquisition covers
\(\max(8,4\cdot\textit{allowedCoreCount})\) visible-window capacities and
creates at most one finite packet per allowed core. Existing results and
reservations are reused span-exactly. Small scroll steps inside this region
therefore require neither cancellation nor a new worker wave.

\section{Worker-side Braille reduction}

Each \texttt{MiniMapWarmup} packet runs on its own finite one-shot worker in the
\texttt{MiniMap} lane. The closure owns the read snapshot, geometry, settings,
source span and version ticket. Packets read sequentially within their bounded
span; no second document model is constructed. The editor-local ledger may
accept packets from an older generation of the same version, while only a
projection matching the current visible key may replace the canvas.

For every sampled line, the worker walks display characters with TVision's
UTF-8 width calculation and the configured tab-stop calculation. Whitespace
does not set density bits. Every occupied display-column span is scaled from
the editor viewport width into the minimap's horizontal dot columns. Braille
mode has twice as many dot columns as body cells; the line mask is a
\texttt{uint64\_t}, so at most 64 horizontal dot columns are retained.

Four line masks and two adjacent dot columns form one Braille cell. Source
lines zero through three select the four dot rows; the left column sets bits
\texttt{01}, \texttt{02}, \texttt{04}, and \texttt{40}, while the right column
sets \texttt{08}, \texttt{10}, \texttt{20}, and \texttt{80}. The resulting
byte indexes the prebuilt glyph table at Unicode code point
\texttt{U+2800 + pattern}. The worker does not create glyph strings in its
payload. It returns the bytes in \texttt{rowPatterns}, plus the document-line
start and end represented by every minimap row, the sampling bounds, total
lines, geometry, and renderer mode.

\section{Result adoption and cache continuity}

The common dispatcher identifies the exact editor through the task ID before
the minimap domain checks owner, generation, document, version, geometry,
mode, and span. Matching packets first extend the bounded ledger. As soon as
all lines of the current visible subwindow are present, that immutable
projection may be adopted even while directional prewarming continues. An
older packet may add reusable coverage but may not overwrite a newer viewport
projection.

Adoption publishes row patterns and the inverse line mapping and requests a
redraw only when visual data changed. Geometry-compatible content may remain
visible while a replacement wave runs, but a payload from an older document
version is never projected. Multiple editors warm independently, including
background windows; their packet waves share neither a focus gate nor a
lane-wide worker.

\section{Bounded reuse and controlled churn}

The warm-window ledger is deliberately domain-specific. Unlike syntax, the
minimap has no forward lexical state to validate; unlike the line index, it
does not establish one global BOF prefix. Its entries are keyed by version,
source span, window alignment, viewport and body geometry, renderer mode, and
all settings that affect display-column reduction. The bounded window count is
the memory policy, not a second document cache.

The first packet implementation proved that worker independence alone is not
enough. Continuous PageDown and large jumps could create ten to twelve
thousand tiny result-ready packets faster than the bounded UI dispatcher could
adopt them. Larger directional acquisition windows, span reservations, and
early visible-window adoption removed that backlog. In the accepted enwik9
run, 100 PageDown followed by 100 PageUp events inside a warmed region created
no MAP wave; a distant jump created at most sixteen packets and returned to
\texttt{MAP:0}.

\section{Overlay masks and TVision projection}

Overlay sources publish immutable, revisioned vectors when selection, search,
dirty state, compiler diagnostics, or File Compare state changes. Finite
component packets convert these inputs to line masks with the same display
width and horizontal scaling as the text projection. A pure selection change
therefore recomputes only the search/selection component. Range hashing and
document-wide mask construction no longer occur in \texttt{draw()}.

For each body cell, \texttt{drawGutter} reads the fully adopted text and overlay
projections. Colour priority remains fixed: error, warning, File Compare
missing, insert, offset, equal, find or selection, changed, then normal. An
overlay may colour an otherwise empty pattern cell so that a blank changed or
diagnostic line remains visible.

The viewport marker is computed independently from the visible interval within
the sampling window and written to \texttt{infoX}. It spans at least three rows
when the gutter height permits. Finally the renderer writes the Braille glyph,
fallback block, separator, and marker into the editor row's ordinary
\texttt{TDrawBuffer}. Leading and trailing placement use the same projection;
the adjacent TVision scrollbar remains an independent view with its own event
semantics.

\part{A coordinated workspace}

\chapter{Bento: one task, several views}

Bento is perhaps the strongest UI idea in \mr{}. It did not begin as an
attempt to invent a generic pane framework or a tiled window manager for the
terminal. The recorded starting point was the split editor. A split made an
immediate editing need visible: one document, two places in that document, and
both places still part of the same editing task. Stabilising those viewports
then exposed the more general question.

A compiler failure calls for source, build output, and a problem list that
lead to one another. File comparison requires two documents, their difference
structure, and change navigation. A macro debugger needs source, output,
variables, and watches around one Execution Session. These are not simply
collections of windows. They are coordinated perspectives on one working
object. Loose top-level windows would make their focus, geometry, lifetime,
and restoration the user's problem. The Bento step was to give the task one
desktop object and let that object own the spatial relationship between its
perspectives.

\texttt{MRBentoBox} is that object. Its layout is a tree: internal nodes split
an area horizontally or vertically, while leaves carry a concrete pane role.
The active leaf, a temporarily maximised leaf, visibility, and divider
positions are part of the same layout state. The box owns this tree, pane
lifetime, standard Bento chrome, and the routing of focus and events. The
leaves are nevertheless ordinary TVision pane windows rather than drawn
imitations of windows. This preserves TVision's ownership of focus, Z order,
drawing, and lifetime while giving the user one coherent workspace.

The difficult part is not dividing a rectangle. A Bento is one TVision desktop
window with several possible child pane hosts, and it must make that plurality
feel like one editor rather than a fight for focus. The box keeps one explicit
active leaf. A mouse click first identifies its leaf in Bento-local
coordinates; changing leaves completes transient input in the previous pane,
selects the new pane host and its editor, and projects the focused frame.
\texttt{Ctrl-Tab} follows the same active-leaf path. Focus is therefore neither
guessed from drawing order nor delegated to a private second event loop.

Event routing is just as deliberate. The outer box handles its own close
frame, title drop-lists, splitters, and workspace commands before it passes an
event on. A divider hit starts a constrained divider drag; a content click or
wheel event is directed to the leaf under the pointer, while a keyboard event
uses the active leaf. Pane chrome is drawn by dedicated frame views, and each
pane keeps its own local editor, scrollbars, and policy. In particular, the
container does not simulate child windows by writing directly to the screen.
It uses normal TVision views, but gives them an explicit routing discipline.

Rendering needs a second discipline. Content, pane chrome, scrollbars, layout,
and overlays have independent dirty reasons. The Bento projection pump
coalesces those reasons; a layout change dominates narrower redraws, whereas a
cursor or selection change need not reconstruct the whole tree. Semantic
changes occur in their owning document, diagnostics, debugger, or compare
model first, and only then mark the relevant projection dirty. This is why a
compound TUI view remains responsive without turning repaint state into a
second hidden model.

That boundary made one construction serve several rather different tasks. In
document-viewport mode, editor leaves share the source buffer so that distant
regions of one document can be edited together. The compiler workspace brings
source, output, and diagnostics into a navigable unit. File Compare joins two
sources to their diff state and change operations. The debugger arranges its
source, output, variables, and watches around the session it observes; the
workspace does not become an alternative owner of debugger truth. Bento
snapshots preserve the layout tree, leaf roles, dividers, active and maximised
leaf, so a workspace can resume the working arrangement rather than merely
reopen a pile of files.

Bento 1.5 adds a closed widget mask to every persisted leaf. The first two
bits mean Fold Gutter and MiniMap; unknown bits are rejected rather than
silently reduced. The existing \texttt{WORKSPACE} payload serialises leaf ID,
role, visibility, and mask, while the older \texttt{bento=v1} form remains
readable with role-specific defaults. Fold spans, minimap projections, ledgers,
owners, tasks, workers, and cores are never persisted. Restore reconstructs
the task arrangement and creates fresh runtime owners.

Problems, Structure, and Functions now have pane-owned finite projection
tasks. \texttt{BDIAG} parses and remaps compiler diagnostics from the snapshot
captured at build start; exactly one terminal parse follows the completed
external command. \texttt{BOUT} performs outline sorting, hierarchy building,
offset resolution, and text formatting from a consistent fold snapshot. Each
pane has at most one active worker and one coalesced newest request. Adoption
checks the exact pane owner, generation, role, documents, versions, and
projection hash before changing text, markers, or status. Reentrant title and
minimap broadcasts are held behind the complete adoption boundary.

Structure and Functions request a complete fold basis only for documents of at
most 20,000 lines and eight MiB. Above either bound they deliberately project
the confirmed visible fold spans and report a partial outline. This is a named
resource boundary, not permission to infer unvalidated structure. Diagnostic
remapping likewise requires a complete observed change chain; an untracked
source commit invalidates old diagnostics until the next build establishes a
new common snapshot.

The Hex editor supplies the sharpest proof of the design. It needs six
simultaneous projections of the same bytes---Hex, Strings, Inspector, Decimal,
Binary, and Octal---and one canonical byte cursor. The first integration was
discarded because it taught \texttt{MRBentoBox} about Hex-specific branches,
gave the primary leaf exceptional treatment, and tried to repair chrome after
drawing. The successor, \texttt{MRBentoHexEditor}, is a specialised Bento
subclass: it reuses the generic layout, pane, focus, and chrome mechanisms,
while owning byte roles, byte cursor, and number-format semantics itself.
That division is what lets Bento be a powerful UI element rather than a
container that gradually learns every feature it contains.

Each of those six panes is also its own \texttt{HexPane} execution owner.
Finite workers prepare immutable offset rows, cell text, string-search halos,
or the Inspector's value rows from a \texttt{ReadSnapshot}. The draw path
consumes that payload and a bounded cursor/edit overlay; it performs no string
search, numeric conversion, or complete pane formatting. At most one request
is active per pane, and a full viewport change therefore has a six-worker
ceiling. Cursor movement inside an adopted viewport reuses all five data-pane
projections; only the cursor-dependent Inspector may require new derived work.
All editable data panes share one byte cursor and one record/column anchor,
while TVision supplies the native cursor only to the focused pane. The logical
record index uses \texttt{size\_t}, but the native TVision scrollbar exposes an
\texttt{int}; fully proportional scrolling above \texttt{INT\_MAX} records is
therefore an explicit support boundary.

File Compare uses a separate ordered pipeline rather than hiding large copies
inside UI adoption. Two pane-owned workers acquire and split the source
snapshots, one worker computes and normalises the Myers edit path, and two
pane-owned workers build the immutable original and compare projections. Thus
one generation is exactly a \(2\rightarrow1\rightarrow2\) sequence. The
Myers frontier orders only that comparison; it does not serialize other Bento
owners or the Compute lane. Navigation uses the adopted change groups without
creating workers, while mutation cancels the old generation and creates a new
five-task sequence.

Bento is not the whole editor family, and that distinction is deliberate.
\texttt{MRSidekickEditor} does not inherit from Bento; it is a \texttt{TView}
for short-lived, code-relative editing. In snippet mode it edits a proposed
replacement range and supports placeholder navigation. In read-only mode it
places explanatory, reference, or diagnostic text beside or beneath the code
that prompted it. A Sidekick belongs to its parent buffer and disappears with
that context; it neither owns a durable workspace nor needs a layout tree. The
two forms demonstrate an important design judgement: a persistent task with
several simultaneous perspectives needs Bento, while a brief local edit or
explanation needs an anchored editor of its own.

\part{MRMAC as an integrated runtime}

\chapter{A language that belongs to the editor}

\mrmac{} is not merely a file of macro commands interpreted at startup. Its
canonical compiler produces in-memory bytecode, while the Macro Catalog owns
loaded files, metadata, profiles, and resident bytecode. That decision joins
extensibility to a clearly identifiable runtime owner.

On-demand compilation is its normal economy. A binding may name a file that
has not yet been loaded; on first use, the source is resolved, canonically
compiled, and then retained in memory. This avoids a large startup burden
without parsing the source again for every execution. An index for warming
bound macro files in advance also exists. The infrastructure is present, but
the current application call path is not connected to it. This manual
therefore does not claim active ``pre-use compilation'' as a delivered feature.

The same restraint applies to debug information. Source maps are created on
the debugging path, not for every ordinary macro execution. There is no second,
secret debug compiler. One compiler, one bytecode model, and additional cost
only where the user actually requests it.

\chapter{Inside the MRMAC virtual machine}
\label{ch:mrmac-vm}

The virtual machine is the point at which \mrmac{} stops being source text and
becomes editor behaviour. It is a compact stack machine, but ``stack machine''
is only the beginning of the useful explanation. The VM also gives values
their storage lifetime, separates local and process-wide runtime state,
dispatches typed language operations into the application, preserves a paused
execution, and produces results that another owner may adopt. Treating it as a
loop over opcodes would miss most of its contract.

Figure~\ref{fig:mrmac-vm-execution-flow} on
page~\pageref{fig:mrmac-vm-execution-flow} follows one compiled macro through
that contract. The compiler, catalog, runner, VM, runtime K/V tree, and UI
thread remain distinct owners. In particular, the diagram does not turn the VM
into a general application object registry: macro-visible runtime values live
in the VM storage model, while live TVision objects and document adoption stay
outside it.

\section{The bytecode image and execution loop}

\texttt{mrmac.c} emits one byte stream containing executable units and their
entry offsets. Integer and real literals are encoded directly behind their
push opcodes; strings and symbolic operation names are zero-terminated
operands. Branch and call instructions carry bytecode offsets. The loaded
image is therefore not an abstract syntax tree retained for later
interpretation. It is the canonical executable form held by the Macro Catalog.

\texttt{VirtualMachine::BytecodeExecution} starts at a selected entry offset
and maintains an instruction pointer, an operand stack, and a return-offset
stack. Push, load, arithmetic, comparison, logic, hash, and array instructions
transform typed operands. \texttt{GOTO} and \texttt{JZ} alter the instruction
pointer; \texttt{CALL} saves the next offset before entering its target, and
\texttt{RET} restores it. Invalid targets, stack underflow, malformed operands,
and type mismatches become VM errors rather than unchecked jumps through the
byte stream.

This design makes the hot path direct. There is no node allocation or visitor
dispatch per source construct, and a normal run does not carry source spans
beside every instruction. The debugger requests a source map from the same
compiler only when a debug start needs the relation between instruction
offsets and source spans. Watch expressions use that frontend in a restricted
expression mode and end in \texttt{HALT}; they are not handed to a second
parser or a general-purpose evaluator.

The complete bytecode run holds the recursive VM execution lock. This is a
semantic boundary, not a claim that a Macro-lane worker is the only worker in
the coprocessor. Runtime environment fields and the global K/V tree are
process-wide, so two independently owned \texttt{MacroJob} workers must not
mutate them concurrently. Worker identity, core assignment, and result
delivery remain independent even where VM state access itself is serialised.

\section{One value model, several lifetimes}

A VM value records its type and the matching payload: integer, real, string,
character, array, or hash handle. Arrays retain typed elements. A hash value
also records whether its handle belongs to the VM-local hash store or to the
central global store. That storage bit is small but decisive: a numeric handle
without its storage domain would not identify a value.

Finite \texttt{DEF\_*} variables normally live in the VM's variable map and
local hash store. Clearing the execution clears unreachable local value trees.
A recurring closure instead restores its declared values from its closure
state, and a long-lived Execution Session restores session variables from
\texttt{EXECSESSIONS}. These are language lifetimes, not namespaces inferred
from source file names. Two macro files do not acquire private globals merely
because they came from different paths.

Process-wide macro state uses the central runtime K/V store. Its named roots
separate responsibilities:
\texttt{MACROGLOBALS} contains explicit application globals,
\texttt{MACROCATALOG} contains loaded macro and bytecode metadata,
\texttt{EXECSESSIONS} contains session and closure state,
\texttt{MODELESSUI} contains retained modeless UI values, and
\texttt{MACRODEBUGGER} contains debugger definitions and live debugger
bookkeeping. These roots share a storage substrate, but they are not one
undifferentiated dictionary.

Hash and hash-array values may cross a storage boundary. In that case the VM
recursively copies the reachable value tree into the target store and marks
the resulting handles with the target domain. Within one store, it may retain
the existing handle. This prevents a global value from referring accidentally
to a local hash that disappears when a finite VM ends. It also explains why
C++ records used during transfer are not allowed to become a second
value-bearing registry beside the K/V tree.

\section{Opcodes end at typed application boundaries}

Pure bytecode operations are only one instruction family.
\texttt{OP\_INTRINSIC} carries a symbolic name and argument count, pops the
arguments in source order, and pushes the typed result returned by
\texttt{MRVMIntrinsics}. Hash inspection, string conversion, environment
queries, search operations, and typed UI inquiries enter through this value
returning boundary.

\texttt{OP\_PROC} similarly carries a name and arguments, but dispatches a
side-effecting procedure. The procedure catalog classifies the operation into
configuration, runtime, editor, or macro families before the corresponding
executor handles it. Variable procedures such as tab expansion have a
separate opcode because their destination is an existing VM variable rather
than an ordinary return value. System variables are reached through the normal
load and store instructions, which gives the VM one place to enforce
read-only state, type rules, and route restrictions.

Symbolic names in bytecode are deliberate. They keep the compiler's signature
tables, the execution profiler, and the VM dispatch vocabulary aligned without
exposing C++ function addresses as language state. They do not make the calls
untyped: the compiler checks signatures, and the VM validates the values again
where runtime state determines what is legal.

The VM is consequently integrated, not sandboxed. An editor procedure may
move a cursor or stage a text mutation; a runtime procedure may start another
macro; a typed UI procedure may update retained modeless state. Integration
does not erase ownership. A worker-side VM receives immutable or copied input
and records a result; it does not gain permission to mutate a TVision view or
publish a document version.

\section{The execution profile chooses the legal route}

Before execution, \texttt{mrvmAnalyzeBytecode} scans the same byte stream and
classifies its opcodes, intrinsics, procedures, and system-variable accesses.
Pure computation is background-safe. Editor and TVision-affine operations
require the UI thread. A bounded subset of editor operations is eligible for
staged background execution, while external I/O remains explicitly visible in
the profile. This analysis is conservative: an unknown or unsupported
operation does not become background-safe by optimism.

The runner turns that profile into the routes whose session lifetimes are
shown in Chapter~\ref{ch:execution-sessions}. At the VM boundary, a UI-affine
macro may use live editor state, a background-safe macro becomes a finite
\texttt{MacroJob}, and a staged-background macro receives a document snapshot,
cursor and selection state, relevant runtime values, and a conflict basis.
Its VM writes a staged edit transaction and deferred UI commands as data.

The route therefore changes the available projection of the application, not
the bytecode language. The same opcode may read a live system variable on the
UI route or its captured staged equivalent on the worker route. Unsupported
UI-affine operations are rejected from staged execution instead of quietly
calling across the thread boundary. The UI thread accepts a staged result only
while its owner and conflict basis still match, changes the model before
projecting deferred UI effects, and discards the whole result on mismatch.
There is no partial repair or implicit rebase.

\section{Yielding, debugging, cancellation, and completion}

A foreground \texttt{DELAY} and a debugger stop both suspend execution without
pretending that the bytecode has completed. The VM preserves the bytecode
image, instruction pointer, call stack, return values, parameter string, and
the route-specific state needed for continuation. A debug stop additionally
records its source identity, stop reason, breakpoints, step policy, and live
variables. Continuing resumes that same execution state; it does not replay
the macro from its first instruction.

The parked VM belongs to the logical Execution Session. It does not justify a
blocked coprocessor worker while a user inspects variables or while a delay
waits for its deadline. A later scheduler or debugger action creates the next
finite execution action. This distinction is what lets session lifetime be
longer than worker lifetime without turning the Macro lane into a collection
of sleeping threads.

Cancellation is cooperative. The bytecode loop checks the active cancellation
request at instruction boundaries, and longer operations must provide their
own bounded checks where interruption is supported. The VM does not terminate
a thread at an arbitrary machine instruction. Likewise, a debugger pause is a
request observed at a safe VM boundary; an intrinsic or procedure is not
half-applied merely to make the pause appear instantaneous.

Completion yields typed effects rather than ownership transfer. A foreground
run leaves its return state and log with the caller. A background run returns
log lines and explicitly requested UI commands. A staged run returns its
transaction, state deltas, deferred UI commands, and conflict basis. A debug
run returns a stop or completion snapshot while the live paused VM remains
owned by its session. In every case, the consumer decides whether and how that
result becomes application-visible.

\section{Bytecode calls and macro calls are different operations}

\texttt{CALL} and \texttt{RET} are intra-image control-flow instructions.
They use the current VM, variable map, operand stack, and bytecode image, and
their return stack contains byte offsets only. They are suitable for compiler
generated control flow whose target is already part of the executable image.
No catalog lookup, source resolution, or new macro identity occurs at that
boundary.

\texttt{RUN\_MACRO} is a language-level macro invocation. Its file-qualified
specification is normalised and resolved through the Macro Catalog, which
provides the target file, entry offset, attributes, execution profile, and
resident bytecode image. The invocation creates a child VM, supplies the
parameter string, propagates the current Execution Session identity, and
selects closure state when the target is a closure unit. The child's log is
joined to the caller's log after execution; transient and dump attributes are
then applied to the catalogued image rather than to the caller's bytecode
stack.

This distinction prevents a source-level macro call from becoming an
unchecked offset jump into whichever image happens to be resident. It also
keeps \texttt{FIRST\_RUN} meaningful per catalogued macro definition and keeps
parameters scoped to the invoked macro. The parent parameter context is
restored after the child finishes, while return and error outputs propagate
through the guarded execution state.

Staged background execution tightens the boundary. It cannot perform an
unplanned lazy file load from a worker. A child macro must already be resident
and included in the captured staged execution context; otherwise the call
fails through the normal runtime error path. This avoids turning a seemingly
finite staged transaction into hidden filesystem I/O and prevents its
execution basis from changing after submission.

Debug execution preserves the same distinction. Stepping into
\texttt{RUN\_MACRO} starts a child debug VM with the target's own source map.
If the child stops, the debugger retains a child frame together with the
parent instruction offset and paused parent VM. Continue and step-out can
therefore return to the real parent execution rather than reconstructing a
synthetic source stack from macro names.

\section{Authority, persistence, and failure containment}

Several parts of this path deliberately know less than their neighbours. The
compiler knows symbols, signatures, source positions, and bytecode layout, but
does not own runtime values. The Macro Catalog knows loaded files, definition
metadata, entry offsets, profiles, and resident images, but does not own a live
instruction pointer. A VM owns one executable state, while an Execution
Session owns the logical identity and lifetime in which that state runs or is
parked. The UI consumes results and debugger projections, but does not keep a
writable copy of VM truth.

The runtime K/V store extends beyond one VM without becoming persistence by
default. Explicit macro globals, modeless values, session state, catalog
metadata, and debugger state are process-runtime data. The workspace boundary
in Chapter~\ref{ch:workspaces} consequently persists domain state, never a VM
instruction pointer, stack, live hash handle, source map, or paused execution.

Settings are a deliberately narrower exception to the usual runtime-only
story. Chapter~\ref{ch:settings-bootstrap} describes the controlled
\texttt{MRSETUP} route from persisted macro source to the authoritative
settings model. It does not make general VM K/V roots serialisable or turn a
runtime global hash into an alternative settings file.

TVision remains on the other side of the same boundary. Typed MMP procedures
may write retained macro-visible values under \texttt{MODELESSUI}; the
projection described in Chapter~\ref{ch:mmp} leaves live windows, focus, Z
order, event dispatch, and drawing lifetime with TVision. A parked VM never
keeps a view pointer alive.

Runtime failure is contained at the execution boundary. Invalid bytecode
operands, type errors, bounds errors, unknown operations, and exceptions from
application procedures end the current run and produce a VM error line. A
background result consequently carries failure instead of throwing through
the result mailbox into the UI loop. The manual does not promise stable
numeric error codes where the implementation provides diagnostic text and
route state.

There are also explicit costs. The process-wide execution lock limits
concurrent VM mutation even when the coprocessor can run many unrelated
non-macro tasks in parallel. Cooperative cancellation cannot interrupt the
middle of an opaque operating-system call. Staged execution supports only the
operations for which captured input and an accountable commit can preserve
semantics. These limits are preferable to three misleading claims: that a
worker implies concurrent VM state, that every procedure can be rolled back,
or that every running macro is safe to move off the UI thread.

\section{Why this is a VM rather than a callback catalogue}

A catalogue of application callbacks could expose editor operations with much
less machinery, but it would not provide a language runtime. Control flow,
expressions, typed locals, arrays, nested hashes, macro calls, closures,
sessions, and debugger continuation would then have to be recreated by the
host around every callback. More importantly, no single executable object
would exist that could be profiled before execution or parked at an exact
instruction.

The bytecode boundary makes source-independent questions answerable. The
runner can count opcodes and named calls, identify UI affinity and external
I/O, and decide whether staging is possible without executing the macro. The
catalog can keep an immutable resident image and exact entry offsets. The
debugger can bind a source span to a bytecode offset and later verify that a
paused VM is still stopped at that offset. These capabilities follow from one
canonical representation; they are not metadata heuristically reconstructed
from a series of callbacks.

The VM also makes extension disciplined. Adding an intrinsic or procedure is
not merely adding a C++ function to a public registry. Its compiler signature,
runtime type checks, execution-profile classification, background/staging
behaviour, error semantics, and documentation must agree. A typed operation
may be powerful---it can start a process, mutate a document, or describe a
modeless window---but the instruction still crosses a named point at which
those obligations can be reviewed.

This is why direct TVision escape hatches would be particularly damaging.
Passing a view pointer or paint callback through a generic VM value would evade
storage lifetime, route profiling, staged-result validation, debugger
inspection, and workspace rules at once. Logical identifiers and retained
typed values are less superficially flexible, but they keep a macro
explainable after the original call has returned.

Nor is bytecode treated as a portable interchange format. Opcode numbers and
operand layout are an internal compiler/VM contract in the current executable
and repository. The Macro Catalog may retain a compiled image for the process
lifetime, but settings and workspaces persist source-level or domain-level
state, not an opaque VM snapshot. This keeps evolution tied to the canonical
compiler rather than creating a bytecode migration problem beside it.

\section{Observability without a shadow runtime}

The VM exposes several different forms of evidence because they answer
different questions. Its execution log records important notices and failures;
ordinary instruction tracing can be disabled for background work, and the log
is bounded to 256 collected lines before one truncation notice is added. Return
integer, return string, error level, parameter string, and macro stack belong
to the active execution state. They describe language execution and are not
substitutes for coprocessor timing or UI messages.

The coprocessor records the surrounding worker lifecycle: submission, assigned
core, running interval, result readiness, acceptance, adoption, discard, and
finish. An Execution Session records logical macro state and recent outcome.
The debugger records source-bound breakpoints and watches, while values shown
at a stop are freshly projected from the live VM, closure/session backing
store, and application globals. A scalar debugger write is validated again by
scope and type at the VM boundary and returns a new snapshot; the variable
pane does not become writable runtime storage.

The global hash store has its own optional read/write-rate and hotspot
instrumentation. That telemetry can show whether runtime K/V access has become
a cost centre without placing counters inside macro-visible hashes or changing
their values. Likewise, execution-profile flags describe possible behaviour
found in bytecode; they do not record what a particular run happened to do.

\chapter{From a broken macro clock to Execution Sessions}
\label{ch:execution-sessions}

The macro clock was a small experiment with a large lesson. Repeating macro
work looked like concurrency, but it had no independent Execution Session.
It therefore lacked identity, ownership, lifetime, cancellation, debuggability,
and a reliable answer to the question of which work was still active.

An Execution Session now describes exactly one logical macro execution: session
ID, owner, route, state, task, and, where applicable, closure belong together.
The scheduler provides time and prevents uncontrolled overlap; it does not
itself decide whether bytecode is UI-affine or suitable for the background.
The runner selects the route: ordinary UI execution, foreground delay,
background, or staged background.

Each background or staged Execution Session submits a finite
\texttt{MacroJob} in the Macro lane. Chapter~\ref{ch:coprocessor-derived-work}
defines that worker and core-assignment path; the session contributes logical
identity and lifetime, not another scheduler. UI-affine and foreground-delay
sessions do not enter the lane, and a paused session retains no worker.

page~\pageref{fig:mrmac-session-routes} separates the routes and their
lifetimes. The runner makes the routing decision; the scheduler is concerned
with interval and overlap policy, while the coprocessor owns only the finite
worker execution and result delivery.

The clock thereby became a shared foundation for recurring closures, modeless
UI callbacks, execution status, and later the debugger. A scheduler that does
not blindly place a second due execution next to the first is not a
convenience-driven restriction. It protects retained UI state and external
work from overlaps that cannot be explained afterwards.

\chapter{MMP: retained UI without a second object world}
\label{ch:mmp}

MMP, the Modeless Macro Programs, were another point at which an apparently
quick shortcut was rejected. Macros were not given raw TVision pointers,
arbitrary paint callbacks, or a second event loop. Instead, they define
retained UI state in the VM K/V model; TVision projects that state as windows,
controls, and input. Timers use the session scheduler, and closing a window
removes its associated timers and callbacks with their owner.

The same boundary lets MMP state and the debugger meet in a Bento workspace
without either view inventing execution truth. Debugger continuation, session
identity, and value ownership remain the VM concerns described in
Chapter~\ref{ch:mrmac-vm}.

\part{The editor as a personal environment}

\chapter{settings.mrmac: canonical bootstrap and executable state}
\label{ch:settings-bootstrap}

\mr{} does not store its configuration as a JSON or YAML data heap.
\texttt{settings.mrmac} is controlled bootstrap source in the language that
belongs to the compiled application. The bootstrap reads the existing state,
checks and normalises it, drops unknown or obsolete ends, adds current defaults,
and writes canonical source with the current Build Epoch.

Figure~\ref{fig:settings-bootstrap-flow} summarises the authority change from
persisted source to the final VM apply.

The file is not then the live runtime owner. The VM executes the startup
\texttt{MRSETUP} path; only the central in-memory settings state governs the
running application. This ``cutting off the old braid'' approach avoids an
ever-growing collection of compatibility lists. On loading, the past is
translated into a current, readable, executable form.

There are explicitly named transitional tensions, including keymap staging
while loading. It is not a hidden second authority, but a bounded exception
because serialisation accesses the canonical keymap model. \texttt{WORKSPACE},
too, is a protected extension of persistence, not an unnoticed part of the
canonical core settings contract.

\chapter{Keymaps as a programmable input language}

The argument over efficient editor interaction does not end with a default.
WordStar, Emacs, and Nano are not folklore in \mr{}; they demonstrate that
interaction is part of a personal way of working. A profile contains
context-dependent canonical key tokens and bindings. The Key Manager makes
this a usable editor feature rather than a configuration-file trick: it lets a
user work with profiles and bindings, choose an action or macro target, and
record a sequence live in canonical keymap syntax. Invalid sequences,
collisions, and terminal/prefix conflicts are diagnosed before the profile
becomes live. The resolver then builds the Keymap Trie as the runtime
projection; the trie is not the feature's user interface, but the structure
that makes its input grammar decidable.

A sequence is not a hard-coded single keystroke. It is stored as a token
sequence and has no fixed length limit in the data model. The resolver may
hold a prefix open, but it forbids terminal/prefix collisions. Thus there is
no ambiguous waiting period in which a completed command might yet turn into a
longer one.

What matters most is the target of a binding. It may be a fast built-in action
or a file-qualified \mrmac{} macro. The user can therefore bind not just
\emph{Save} or \emph{Cursor Left}, but their own complex, reviewable automation
to their input language. This freedom is not unbounded: profile, context,
token parser, trie, and the distinction between action and macro give it a
form that can be understood.

\chapter{Profiles and automatic setup}

File-extension profiles associate one or more selectors with effective editing
settings, a window theme, and, where necessary, a compiler profile. A C++
project, a \LaTeX{} document, and a shell script thereby receive not only a
different colour, but an appropriate working environment. These profiles, too,
are described through \texttt{settings.mrmac}, not hidden in a second, loose
registry.

Compiler auto-setup extends the same idea. It finds known tools on
\texttt{PATH}, probes their version and characteristics, and creates or
completes profiles for toolchains that are actually present. That avoids empty
configuration forms without pretending to understand every possible build
system automatically. A profile remains visible and editable, and may include
build hooks and MRMAC actions.

\part{Syntax as a shared core}

\chapter{From an external generator to an integrated syntax model}

The first attempt to recognise \mrmac{} sources used Lex and Bison. That
approach proved outdated and did not provide a viable foundation for an editor
whose language knowledge must serve colouring, folding, and indentation at
the same time. The version history preserves at least the trace of removing
the Flex/Bison material; the engineering lesson matters more than the archive:
a parser generator does not itself solve the problem of an integrated,
incrementally usable editor model.

The present core combines classification by path, extension, and content probe
with shared line state and token runs, plus concrete rules for individual
languages. It deliberately does not claim to be a complete universal grammar.
Each language supplies its syntax state and token runs through the same
contract as the others; folding, outline, colouring, and indentation decisions
can reuse those results. \mrmac{} is consequently not a foreign C component
beside the editor, but a language in its own syntax model.

The current tree has 24 language modes, including Plain Text, not 384.
Automatic recognition combines file names, extensions, and a bounded content
probe. The number is smaller than the perceived breadth of the editor, but it
is the honest number. A later Tree-sitter trace was also removed from the
repository; the history proves the removal, but does not establish its exact
reason without further sources. This manual does not invent one afterwards.

\chapter{Trainers: the workbench for language features}

The trainers are not machine learning. They are a workbench on which language
rules become visible, repeatable, and discussable against real examples. The
fold trainer automatically classifies an input when needed and emits its fold
structure as numbered ASCII. The outline trainer uses the same fold scan to
produce the outline.

The indent trainer goes further. It creates a real \texttt{MRFileEditor},
varies language, indentation style, UI style, and tab treatment, and simulates
Enter and Smart Undent. Its strict pass/fail expectations therefore exercise
production paths rather than an independently invented test semantics.

The trainers do not prove the entire visible behaviour under load; they are no
replacement for UI or coprocessor checks. They do secure the exact semantic
question that they show: which structure, outline element, and indentation
decision follows from this text? That is valuable testability because it is
made of the same language as the editor feature.

\part{Spaces and the Unix world}

\chapter{Virtual desktops and resumable workspaces}
\label{ch:workspaces}

A terminal editor need not be reduced to a single document window. \mr{}
assigns every desktop-capable window to a virtual desktop. When changing
desktops, windows on the other desktop are hidden, not destroyed; focus,
geometry, and state remain intact. Windows can be moved, minimised, tiled, and
cascaded without those desktop operations needing to know the domain nature of
an editor, a Bento view, or a modeless macro window.

A workspace makes this spatial working state recoverable. It stores, among
other things, URLs, window geometry, cursor positions, virtual desktop,
minimised and restore state, and Bento snapshots for suitable windows. Autoload
and autosave do not turn it into an all-powerful persistence layer; they make
it a deliberately bounded continuation of personal work.

Runtime execution identity is intentionally absent. Workspace restore does not
serialise or recreate worker ordinals, task IDs, OS threads, core assignments,
packet reservations, or warmed ledgers. It restores windows, panes, widget
masks, and domain state; constructors and restored demand then create new
execution owners and fresh packets. Background windows continue their work
after restore without inheriting a stale worker lifetime.

The result is a TUI workspace in which many windows need not form an
unmanageable parade. They can live on virtual desktops and reappear in a
workspace exactly where work was interrupted.

\chapter{MFS and Acquire: Unix output as working material}

Multi-file search and multi-file replace combine recursive file work with
PCRE2 and can be restricted to the workspace. This is not merely a search box
with a different file dialog. It is a bridge between the open workspace and
the file tree.

MFS remains modal so that editor snapshots and replacement offsets cannot
silently become stale through concurrent editing. Directory traversal, chunked
file I/O, snapshot materialisation, and PCRE2 matching nevertheless run in a
finite dialog-owned coprocessor task. The dialog reports collection and
\texttt{x/y} search progress. Its Search button becomes Cancel while work is
running. Cancellation is checked during traversal, between I/O chunks, between
matches, and through PCRE2 automatic callouts inside a long individual match.
Only a complete, still version-valid session reaches the result dialog.
Replace All remains a UI-thread mutation phase, but performs one replacement
per dialog event and reports \texttt{x/y} progress. Matches are applied from
the end of each file so that earlier offsets remain valid without rescanning
the complete file after every edit. Cancel pauses the mutation and offers
Continue, Abort, or Revert. Abort retains the completed prefix as individual
Undo records. Revert restores one pre-operation snapshot per touched file and
removes only the Undo suffix owned by that Replace All run; it does not replay
thousands of Undo commands or construct a corresponding Redo stack.

Acquire follows another, particularly terminal-native idea. \mr{} runs a
shell command out of sight, reads its standard output, and interprets each line
as a candidate readable path. Candidates are resolved and deduplicated; the
user may open or load selected files or every discovered file. The process
group runs in a finite I/O worker and stdout is adopted incrementally. The list
shows per-entry ordinals and a total. Closing the dialog cancels the process
group, waits for its bounded TERM/KILL teardown, and discards unadopted output.
Loading all files is sliced at file boundaries so that Close can stop the
remaining queue. Acquire is therefore not the uncritical insertion of arbitrary
pipe bytes into a buffer. It turns Unix tools into an understandable file
selection.

\part{Decisions that left traces}

\chapter{The Hex restart and the LSP train}

The first Hex integration was discarded. Its lesson was specific: a Hex view
does not belong as a special branch in a generic BentoBox; it needs neither an
exception to the normal pane lifetime nor a self-drawn frame. Restarting it as
\texttt{MRBentoHexEditor}, with six ordinary pane windows, shared byte-cursor
logic, and the same document basis, was not cosmetic refactoring. It restored
clear responsibility. Moving string recognition, Inspector conversion, and
numeric formatting from \texttt{draw()} into six pane-owned immutable
projections completed that responsibility: the Hex restart now separates the
shared byte model, derived worker data, and TVision projection in the same way
as the rest of the editor.

The LSP train was more painful. Two attempts consumed weeks; the architecture
could not be shaped into a viable editor feature. The history ultimately
records the removal of the LSP material in a large rollback. This is not a
claim that LSP is inherently bad. It is the specific conclusion that an
external IDE model could not be integrated with adequate clarity and benefit
into this project's existing runtime, UI, and working model.

Both stories belong in the manual because discarding work can be a technical
ability. A system remains coherent not by saving every line once written, but
by being able to remove the wrong boundaries again.

\chapter{Measured limits, not wishful thinking}
\label{ch:measured-limits}

The subsystem evidence described in
Chapters~\ref{ch:coprocessor-derived-work} and~\ref{ch:mrmac-vm}, together with
trainers and the live log, makes technical claims open to challenge. This
chapter records measured outcomes and limits rather than defining those
telemetry contracts a second time.

The correction train also preserved quantitative counterexamples. Repeated
random line addressing made the original enwik9 display-width pass run for
more than six minutes; one initial address plus linear \texttt{nextLine}
reduced the 13,147,026-line generation to 5.434--6.384 seconds including
debugger stops. Syntax packet density fell from 7.00 to 4.07 packets per
generation, and display-width result churn for the measured version sequence
fell by 92.8 percent. HexBento's combined navigation bursts settled in
0.13--0.17 seconds, and an identical 954-MiB File Compare remained responsive
and closed without residual workers.

These numbers do not make a high absolute one-shot count a defect by itself.
The relevant conditions are bounded packets, exact owners, strict modulo core
assignment, no lane-wide serialization, bounded UI adoption, and complete
return to zero after load or close. An exceptional single long line remains
sequential within its width packet; syntax and folding remain ordered at their
validation fronts; a genuinely blocking external stream may retain its own
worker. Those are measured and named limits, not concealed scheduler queues.

The build belongs to this story as well. It orchestrates the TVision upstream,
the MRMAC compiler, training programs, regression checks, and manuals. A clean
rebuild is not a ritual; it tests whether the delivery form claimed by the
repository can actually be produced from its source. The manually maintained
Bento header dependencies are not yet complete, so a header-layout change is
trusted only after \texttt{make clean all CXX=clang++}; an incremental link may
otherwise combine ABI-incompatible objects.

\chapter*{Outlook}
\addcontentsline{toc}{chapter}{Outlook}

The technical centre of \mr{} is not one individual trick. It is the repeated
application of the same attitude: do not copy original data unnecessarily,
decouple derived work from interaction, give truth one unambiguous owner, and
place extensibility under the same boundaries as built-in code. This is why a
gigabyte document can become useful immediately, a Braille minimap can exist
in a console, a user can program an input language, and a deferred macro can
remain debuggable.
